# Auditoría de serialización del backend

## 1. Resumen y metodología

Auditoría de las 31 rutas de aplicación declaradas en `services/api/app/main.py` y en sus seis routers. El total excluye los endpoints de documentación que FastAPI genera automáticamente (`/docs`, `/redoc` y `/openapi.json`). La rama activa era `feature/serialization-audit-and-implementation`. No se abrió ningún archivo `.env*`; no se modificaron dependencias.

La línea base previa, indicada en [services/api/README.md](../services/api/README.md), pasó **122/122 tests** antes de esta fase. La suite final se ejecutó desde la raíz con `JWT_SECRET_KEY` de prueba, `PYTHON_DOTENV_DISABLED=1` y `uv run --locked --group test python -m unittest discover -s services/api/tests -t .`: **126 tests, 126 aprobados, 0 fallidos, en 48.759 s**. `PYTHON_DOTENV_DISABLED=1` impidió cargar cualquier archivo `.env*`; `--locked` evitó modificar `uv.lock`. Se observó 1 warning de deprecación de Starlette/httpx. La orden inicial `uv run pytest services/api/tests` no es la orden de suite documentada y produjo 12 errores de colección: `ModuleNotFoundError` para `services`/`scripts` y falta de `sqlmodel`/`sqlalchemy` en el intérprete global (`/usr/local/python/3.14.2`), en vez del entorno del proyecto `.venv`.

La configuración define el grupo `test` (no `dev`) y el README especifica `unittest discover` con `-t .` desde la raíz. `uv run --locked --group test` ejecutó la suite con el entorno del proyecto y no permitió modificar `uv.lock`; no se modificaron `pyproject.toml` ni archivos de dependencias. Para clasificar, una anotación de retorno como `-> dict[str, str]` **no cuenta** como `response_model` explícito. ✅ requiere un `response_model` explícito adecuado; ⚠️ indica un modelo explícito que expone datos innecesarios o no coincide con lo que necesita el cliente observado; ❌ indica un dict sin `response_model` explícito. Las respuestas `204` sin cuerpo y el fichero CSV no tienen un cuerpo JSON que serializar: declaran `response_model=None` de forma explícita en el decorador y cuentan como ✅. En la clasificación original de la Fase 1 se trataron como casos aparte; tras la revisión se declaran con `response_model=None` (véanse las secciones 5 y 8).

### Verificación de las sospechas

- **(a) Verificada y corregida:** los cuatro `POST /auth/*` ya declaran modelos explícitos en sus decoradores: `TokenResponse` para login y `MessageResponse` para las tres operaciones de contraseña. El login no incluye email ni contraseña; las respuestas restantes solo incluyen `message`.
- **(b) Verificada y corregida:** `POST /users` usa ahora `RegistrationResponse(id)` y no devuelve email, contraseña ni hash. El caller del backoffice descarta el body y no se encontró un lector de la respuesta en `uis/website`. `GET /auth/me` mantiene `email` y `role` deliberadamente. `UserResponse` de gestión sigue incluyendo email propio y excluyendo `hashed_password` ([models.py](../services/api/models.py)).
- **(c) Verificada y corregida:** `ProfileResponse` es ahora independiente de `ProfileCreate` y declara `id,user_id,name,phone,address`. Se conservan `id` y `user_id` porque el validador frontend los exige. `AuthMeResponse` anida este perfil como proyección tipada. Véanse el parser [account.ts](../uis/backoffice/services/account.ts) y la vista [account-profile.tsx](../uis/backoffice/components/account-profile.tsx).
- **(d) Verificada y corregida:** `SupplierResponse` es ahora independiente de `Supplier` y conserva `id,name,country,categories,rate_per_unit,currency,status,updated_at,contact_email,notes`. El parser frontend requiere también `contact_email` y `notes`, aunque el listado solo renderiza siete de esos diez campos; no se retiraron. Referencias: [models.py](../services/api/models.py), [suppliers.ts:45](../uis/backoffice/services/suppliers.ts#L45) y [supplier-directory.tsx:143](../uis/backoffice/components/supplier-directory.tsx#L143).
- **(e) Verificada y corregida:** summary usa ahora `IncidentSummary` y analyze usa `IncidentAnalysisResponse`, ambos con `response_model` explícito. Sus formas se conservan; `satisfaction.average` admite `null`. Referencias: [incidents.py](../services/api/routes/incidents.py) y [main.py](../services/api/app/main.py).
- **(f) Confirmada:** `InventoryMovementRead` expone `user_uuid` como `str`. La API lo rellena con `str(current_user.id)`; el backoffice lo valida y lo muestra como usuario en escritorio y móvil. Es un contrato actualmente consumido, aunque el nombre sugiera UUID. Referencias: [schemas.py:76](../services/api/inventory/schemas.py#L76), [inventory.py:236](../services/api/routes/inventory.py#L236), [inventory-orders-list.tsx:128](../uis/backoffice/components/inventory-orders-list.tsx#L128) y [inventory-orders-list.tsx:158](../uis/backoffice/components/inventory-orders-list.tsx#L158).
- **(g) Confirmada:** `GET /api/incidents` responde con `Incident`, cuyo `description` es completa; la lista de incidencias la muestra sin truncar. No se debe acortar ni retirar. Véanse [models.py:103](../services/api/models.py#L103) y [incident-list.tsx:253](../uis/backoffice/components/incident-list.tsx#L253).
- **(h) Confirmada, fuera de alcance:** `GET /users` y `GET /users/{user_id}` solo dependen de `get_current_user`; no se observa una comprobación adicional de rol. Se registra como observación de autorización, no como defecto de serialización ni propuesta de cambio en esta fase. Véanse [users.py:62](../services/api/routes/users.py#L62) y [users.py:69](../services/api/routes/users.py#L69).
- **(i) Verificada y documentada:** `GET /api/incidents/results/export` devuelve un `Response` `text/csv; charset=utf-8`, con descarga `results.csv`; el servicio frontend descarga un blob y no interpreta filas. La operación declara en OpenAPI `200 text/csv` con descripción y `404 application/json`. Véanse [main.py](../services/api/app/main.py) y [incident-analysis.ts:63](../uis/backoffice/services/incident-analysis.ts#L63).

## 8. Corrección tras revisión

En la revisión se señaló que los dos `DELETE` con `204` y la descarga CSV no declaraban `response_model` en su decorador, aunque estaban documentados en OpenAPI. La rúbrica exige que cada endpoint declare su `response_model` de manera explícita y no recoge excepciones, así que se añadió `response_model=None` a esas tres rutas. Fue una corrección pedida en la revisión.

**Cambios aplicados:**

- **`DELETE /users/{user_id}` [users.py:125](../services/api/routes/users.py#L125):** Decorador antes `@router.delete("/{user_id}", status_code=status.HTTP_204_NO_CONTENT)`. Ahora: `@router.delete("/{user_id}", response_model=None, status_code=status.HTTP_204_NO_CONTENT)`. La lógica del endpoint y la respuesta sin contenido se mantienen idénticas. OpenAPI sigue declarando `204` sin `content`.

- **`DELETE /suppliers/{id}` [suppliers.py:95](../services/api/routes/suppliers.py#L95):** Decorador antes `@router.delete("/{id}", status_code=status.HTTP_204_NO_CONTENT)`. Ahora: `@router.delete("/{id}", response_model=None, status_code=status.HTTP_204_NO_CONTENT)`. La lógica del endpoint y la respuesta sin contenido se mantienen idénticas. OpenAPI sigue declarando `204` sin `content`.

- **`GET /api/incidents/results/export` [main.py:239](../services/api/app/main.py#L239):** Decorador antes `@app.get(..., response_class=Response, responses={...})`. Ahora: `@app.get(..., response_model=None, response_class=Response, responses={...})`. La lógica del endpoint y la respuesta `text/csv` se mantienen idénticas. OpenAPI sigue declarando `200 text/csv` sin `application/json` implícito, y `404 application/json`.

**Verificación del contrato OpenAPI:**

Se ejecutó `app.openapi()` en runtime y se verificó que:
- `DELETE /users/{user_id}` responde `204` con `content: false` (sin cuerpo).
- `DELETE /suppliers/{id}` responde `204` con `content: false` (sin cuerpo).
- `GET /api/incidents/results/export` responde `200` con solo `content: {"text/csv": {...}}` (sin `application/json`), y `404` con `content: {"application/json": {...}}`.

**Test estructural y sus límites:**

El test `test_all_api_routes_have_response_models_or_declared_exceptions` (el nombre conserva por razones históricas la palabra "exceptions") comprueba que las rutas cuyo `route.response_model` es `None` coincidan exactamente con el conjunto de estas tres rutas. FastAPI **no** permite distinguir, a partir de las rutas registradas, un `response_model=None` indicado de forma explícita de uno omitido: en ambos casos `route.response_model` vale `None`. Por tanto el test garantiza que cualquier otra ruta tenga un esquema de respuesta y que estas tres sean las únicas sin esquema Pydantic, pero no puede verificar por sí solo que cada una escriba `response_model=None` en su decorador. Esa parte se verifica por revisión directa del código de los tres decoradores, enlazados arriba. Esta corrección no cambia el comportamiento que observa el test, por lo que sigue siendo válido:

```python
expected_exceptions = {
    ("DELETE", "/users/{user_id}"),
    ("DELETE", "/suppliers/{id}"),
    ("GET", "/api/incidents/results/export"),
}
routes_without_models = {
    (method, route.path)
    for route in routes
    for method in route.methods
    if route.response_model is None
}
self.assertEqual(routes_without_models, expected_exceptions)
```

El test comprueba a continuación el contrato OpenAPI: que los dos `DELETE` no incluyan `content` en la respuesta `204`, y que el CSV solo incluya `text/csv` (sin JSON implícito).
